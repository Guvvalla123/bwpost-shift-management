===============================================================================
  BWPOST SHIFT MANAGEMENT — SECURITY OVERVIEW
  Date: March 11, 2026
===============================================================================

This file documents every security measure protecting the application,
where it's implemented, and what advanced protections can be added later.


===============================================================================
  ACTIVE PROTECTIONS (currently implemented)
===============================================================================

1. SECURITY HEADERS (Helmet.js)
   File: backEnd/server.js
   What it does:
     - X-Frame-Options: DENY — prevents clickjacking (embedding your site in iframes)
     - X-Content-Type-Options: nosniff — stops browsers from MIME-sniffing
     - Strict-Transport-Security (HSTS) — forces HTTPS connections
     - X-XSS-Protection — enables browser XSS filter
     - Referrer-Policy — controls what URL info is sent to other sites
     - Content-Security-Policy — restricts resource loading sources

2. NOSQL INJECTION PREVENTION
   File: backEnd/server.js (express-mongo-sanitize)
   What it does:
     - Strips $ and . from user inputs (req.body, req.query, req.params)
     - Prevents attackers from injecting MongoDB operators like:
       { "email": { "$gt": "" } } — which would match all users
     - Without this, an attacker could bypass login by manipulating queries

3. XSS (CROSS-SITE SCRIPTING) PREVENTION
   File: backEnd/server.js (xss-clean)
   What it does:
     - Sanitizes all user input to remove HTML/script tags
     - Prevents attackers from injecting <script>alert('hacked')</script>
     - Also protected by HTTP-only cookies (scripts can't read tokens)

4. CSRF (CROSS-SITE REQUEST FORGERY) PROTECTION
   File: backEnd/server.js (custom csrfProtect middleware)
   What it does:
     - Checks the Origin header on all POST/PUT/DELETE/PATCH requests
     - Only allows requests from your Vercel frontend domain
     - Blocks malicious sites from making requests on behalf of logged-in users
     - Example attack blocked: evil-site.com submitting a form that
       deletes employees using your logged-in session

5. CORS (CROSS-ORIGIN RESOURCE SHARING)
   File: backEnd/server.js
   What it does:
     - Only allows API requests from:
       * https://bwpost-shift-management.vercel.app (production)
       * http://localhost:5173 (development)
     - All other origins are blocked
     - In production, requests with no Origin header are blocked
     - credentials: true allows cookies to be sent cross-origin

6. RATE LIMITING
   Files: backEnd/server.js, backEnd/routes/userRoutes.js
   What it does:
     Global (server.js — production only):
       - Max 100 requests per IP per 15 minutes
       - Prevents DDoS and abuse
     Auth-specific (userRoutes.js):
       - Max 10 login/register attempts per IP per 15 minutes
       - Prevents brute-force password guessing
       - Returns "Too many attempts, please try again after 15 minutes"

7. AUTHENTICATION — HTTP-ONLY COOKIES
   File: backEnd/controllers/userController.js
   What it does:
     - JWT access token stored in HTTP-only cookie (15 min expiry)
     - Refresh token stored in HTTP-only cookie (7 day expiry)
     - HTTP-only means JavaScript CANNOT read these cookies
     - Even if XSS happens, attacker cannot steal tokens
     - secure: true in production — cookies only sent over HTTPS
     - sameSite: "none" — required for Vercel ↔ Render cross-origin

8. REFRESH TOKEN ROTATION
   File: backEnd/controllers/userController.js
   What it does:
     - Every time a token is refreshed, a NEW refresh token is issued
     - The old refresh token is overwritten in the database
     - If an attacker steals a refresh token, it becomes invalid
       after the real user refreshes
     - Prevents session hijacking via stolen refresh tokens

9. PASSWORD SECURITY
   Files: backEnd/models/userModel.js, backEnd/validators/uservalidators.js
   What it does:
     - Passwords hashed with bcrypt (10 salt rounds) before storage
     - Even if database is leaked, passwords cannot be reversed
     - Registration requires: min 8 chars, uppercase, lowercase,
       number, and special character (!@#$%^&*)
     - Role field removed from registration — no privilege escalation

10. INPUT VALIDATION (Joi)
    File: backEnd/validators/uservalidators.js
    What it does:
      - Validates all user input BEFORE it reaches the database
      - Email must be valid format
      - Username: 3-30 characters
      - Password: complexity requirements enforced
      - Invalid input returns clear error messages
      - Prevents malformed data from corrupting the database

11. ROLE-BASED AUTHORIZATION
    File: backEnd/middlewares/authMiddleware.js
    What it does:
      - Every protected route checks: (1) valid JWT, (2) correct role
      - Employees cannot access manager routes
      - Managers cannot access employee-only routes
      - Authorization checked BEFORE any database operation

12. OWNERSHIP VERIFICATION
    Files: backEnd/controllers/managerController.js,
           backEnd/controllers/requestController.js,
           backEnd/controllers/attendanceController.js
    What it does:
      - Managers can only manage shifts THEY created
      - Managers can only approve/reject requests for THEIR shifts
      - Employees can only check in/out for themselves
      - Managers can check in/out other employees (verified role)
      - Prevents horizontal privilege escalation

13. SSRF (SERVER-SIDE REQUEST FORGERY) PREVENTION
    File: backEnd/controllers/userController.js (isValidImageUrl)
    What it does:
      - Profile image URLs validated before saving
      - Only allows HTTPS URLs from:
        * res.cloudinary.com
        * images.unsplash.com
      - Blocks javascript: URIs, internal IPs, arbitrary domains
      - Prevents attackers from making the server request internal resources

14. REGEX INJECTION (ReDoS) PREVENTION
    File: backEnd/controllers/managerController.js
    What it does:
      - Search inputs escaped before being used in regex queries
      - Special characters (.*+?^${}()|[]\) are escaped
      - Prevents "evil regex" patterns that cause infinite backtracking
      - Without this, a crafted search string could hang the server

15. SECRET MANAGEMENT
    Files: backEnd/.env, frontEnd/vite-project/.env
    What it does:
      - All secrets stored in .env files (never hardcoded)
      - .env files listed in .gitignore (not committed to git)
      - Production secrets set via Vercel/Render dashboards
      - JWT secrets rotated (old exposed ones are useless)
      - Frontend secrets (Google OAuth, Cloudinary) use VITE_ prefix

16. BODY SIZE LIMIT
    File: backEnd/server.js
    What it does:
      - express.json({ limit: "10kb" }) caps request body size
      - Prevents attackers from sending massive payloads
      - Protects against denial-of-service via memory exhaustion

17. GRACEFUL SHUTDOWN
    File: backEnd/server.js
    What it does:
      - SIGTERM/SIGINT handlers close server and database cleanly
      - Prevents data corruption during deployment restarts
      - 10-second timeout fallback if connections hang

18. DATABASE CONNECTION RESILIENCE
    File: backEnd/config/db.js
    What it does:
      - Retries MongoDB connection up to 5 times with 3s delays
      - Logs disconnection and error events
      - Prevents silent database failures


===============================================================================
  HOW COMMON ATTACKS ARE BLOCKED
===============================================================================

ATTACK: SQL/NoSQL Injection
  Blocked by: express-mongo-sanitize (#2) + Joi validation (#10)
  Example: { "email": { "$gt": "" } } → stripped to { "email": "" }

ATTACK: Cross-Site Scripting (XSS)
  Blocked by: xss-clean (#3) + HTTP-only cookies (#7)
  Example: <script>document.cookie</script> → sanitized + cookies unreadable

ATTACK: Cross-Site Request Forgery (CSRF)
  Blocked by: Origin header check (#4) + SameSite cookies (#7)
  Example: evil-site.com form submit → Origin mismatch → 403 Forbidden

ATTACK: Brute-Force Login
  Blocked by: Rate limiting (#6) — 10 attempts per 15 min per IP
  Example: Automated password guessing → blocked after 10 tries

ATTACK: Session Hijacking
  Blocked by: HTTP-only cookies (#7) + refresh token rotation (#8)
  Example: Stolen token → invalidated on next legitimate refresh

ATTACK: Privilege Escalation
  Blocked by: Role removed from registration (#9) + authorization (#11)
  Example: { "role": "manager" } in register body → ignored

ATTACK: Data Theft via Exposed Secrets
  Blocked by: .env in .gitignore (#15) + rotated secrets
  Example: Old JWT_SECRET from git history → doesn't work anymore

ATTACK: DDoS (Denial of Service)
  Blocked by: Rate limiting (#6) + body size limit (#16)
  Example: 1000 requests/sec → blocked after 100, large payloads rejected

ATTACK: Clickjacking
  Blocked by: Helmet X-Frame-Options (#1)
  Example: Your site in an iframe on evil-site.com → blocked by browser

ATTACK: SSRF (Internal Network Access)
  Blocked by: URL validation (#13)
  Example: profileImage: "http://169.254.169.254/metadata" → rejected


===============================================================================
  FUTURE IMPROVEMENTS (not yet implemented)
===============================================================================

1. ACCOUNT LOCKOUT
   What: Lock account after 5 failed login attempts for 30 minutes
   Why: Rate limiting is per-IP; attackers with multiple IPs can bypass it
   How: Add failedLoginAttempts + lockUntil fields to User model

2. TWO-FACTOR AUTHENTICATION (2FA)
   What: TOTP-based 2FA using Google Authenticator or similar
   Why: Even if password is stolen, account requires a second factor
   How: Use speakeasy or otplib package, add QR code setup in Settings

3. AUDIT LOGGING
   What: Record who did what and when (shift created, employee deleted, etc.)
   Why: Accountability, forensics, compliance
   How: Create AuditLog model, log actions in controllers

4. CONTENT SECURITY POLICY (CSP)
   What: Strict policy controlling which scripts/styles/images can load
   Why: Extra XSS protection layer — even if input sanitization fails
   How: Configure helmet.contentSecurityPolicy with allowed sources

5. PER-USER RATE LIMITING
   What: Rate limit by user ID, not just IP address
   Why: A logged-in user could spam API endpoints from one session
   How: Use express-rate-limit with a custom keyGenerator using req.user.id

6. API REQUEST LOGGING & MONITORING
   What: Log failed logins, permission denials, suspicious patterns
   Why: Detect attacks in real-time, respond before damage
   How: Winston/Pino logger + cloud monitoring (Datadog, Sentry, etc.)

7. GIT HISTORY CLEANUP
   What: Remove .env files from git history completely
   Why: Old commits still contain MongoDB URI, old JWT secrets
   How: git filter-branch or BFG Repo Cleaner, then force push
   IMPORTANT: Change MongoDB password in Atlas after cleanup

8. DEPENDENCY VULNERABILITY SCANNING
   What: Regularly check npm packages for known vulnerabilities
   Why: A vulnerable dependency can expose the entire app
   How: Run "npm audit" regularly, or use Snyk/Dependabot

      - authMiddleware (JWT verification)
      - authorize("role") (role check)
      - authLimiter (login/register rate limit)
      - validate(schema) (Joi validation)
